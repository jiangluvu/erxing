# 播刻技术优化报告（Phase 1 & 2）

## 一、Phase 1 目标

让"文章→播客"的生成质量达到可直接发布的标准。核心聚焦四个维度：
- **节奏自然**：对话有呼吸感，不是机器连读
- **信息完整**：长文章不遗漏关键论点
- **角色稳定**：两个主播音色、风格差异鲜明
- **工程可靠**：生成过程稳定、可预期

---

## 二、Phase 1 已完成优化项

### 2.1 智能停顿插入

**问题**  
Edge-TTS 合成后的音频是连续的，两句对话之间没有停顿，听起来像机器在赶时间，完播率低。

**调研过程**  
用户提出的问题不是"怎么加停顿"，而是"**现在插入停顿比较流行的方法是什么，有没有高级点的办法**"。这说明用户想要的是行业最佳实践，而不是凑活的方案。为此我们调研了从基础到前沿的四个层级：

**层级一：固定停顿（基线方案）**
- 原理：每轮对话后无脑插入 0.3–0.5s 静音。
- 实验：直接实现，发现陈述句和问句没有区别，听起来还是机械。
- 结论：过于粗糙，只能作为保底，不能作为主方案。

**层级二：标点规则停顿（改进方案）**
- 原理：根据句尾标点动态决定时长。问号长一点（0.8s），句号短一点（0.4s）。
- 实验：比固定停顿好，但无法处理没有标点的语气词（"对吧""你看"），也无法区分反问句和设问句。
- 结论：有效，但不够"高级"。

**层级三：LLM 原生韵律标注（理论上最优，实际不可行）**
- 原理：在 system prompt 里要求模型输出韵律标注，例如 `[pause:0.9s]` 或 `<break time="800ms"/>`，后端解析后注入音频。
- 实验：我们对 deepseek-v4-flash 做了多轮 prompt 工程，包括：
  - 明确指令"你必须在对话中插入 pause 标记"
  - 给出完整的 few-shot 示例（带 `[pause]` 的完整对话）
  - 使用"必须执行""严格遵守"等强约束词
- 结果：**模型完全忽略所有韵律标注指令，输出零个 pause 标签**。
- 结论：deepseek-v4-flash 对结构化标注的遵循度极低，此方案在当前模型下不可行。如果未来换用 Claude 3.5 Sonnet 或 GPT-4o，此方案可重新评估。

**层级四：后端规则 + ffmpeg 拼接（最终选中）**
- 原理：LLM 只管输出高质量纯文本，停顿逻辑完全交给后端规则引擎。根据句尾语气词、标点、关键词判断对话情绪，计算对应停顿时长，用 ffmpeg 生成静音片段插入到 TTS 片段之间。
- 实验验证：
  - 先用 edge-tts 直接测试了 `<break time="500ms"/>` 的 SSML 支持，确认有效。
  - 用 ffmpeg `anullsrc=r=24000:cl=mono` 生成指定时长的静音 MP3，再与 TTS MP3 用 concat 拼接，音质无损失。
- 决策理由：不依赖模型配合、100% 可控、效果立竿见影、规则可逐步迭代。

**实现**
- 函数：`_compute_pause(text) -> float`
- 规则（经过多轮试听调整后确定）：
  - 问句（吗/呢/吧/如何/为什么/多少）→ 0.9s（给听众思考/反应时间）
  - 感叹句 → 0.6s
  - 过渡/总结词（总之/所以/接下来/最后/好了/你看/对吧/对吗/嗯/啊）→ 0.7s
  - 普通句号 → 0.5s
  - 其他 → 0.4s
- 技术：ffmpeg `anullsrc` 生成静音 MP3，再与 TTS 片段 concat

**效果**  
问句后的长停顿让对话有了"呼吸感"，不再是连续轰炸。播客收听测试中，"听感疲劳度"明显下降。

### 2.2 SSML 韵律增强

**问题**  
数字、百分比、金额等关键信息在 TTS 中缺乏强调，听众容易漏掉核心数据。

**调研过程**  
用户问"**SSML 方案选哪个**"。这个问题的前提是我们已经知道 edge-tts 支持 SSML，需要决定的是"谁来负责生成 SSML 标签"。

**路径 A：LLM 原生输出 SSML（理想方案，实验失败）**
- 原理：在 system prompt 中要求模型直接输出带 SSML 标签的对话文本，例如 `小羊：<emphasis level="moderate">增长30%</emphasis>，这个数据很关键。<break time="300ms"/>`
- 实验：对 deepseek-v4-flash 进行了严格的 prompt 工程：
  - 在 system prompt 中明确定义 SSML 标签用法
  - 给出 3 组 few-shot 示例，每轮对话都包含 `<emphasis>` 和 `<break>`
  - 使用"必须执行""严格遵守输出格式"等约束
  - 甚至威胁"如果不输出 SSML 标签则视为失败"
- 结果：**模型完全拒绝输出任何 SSML 标签**，始终返回纯文本。推测原因：deepseek-v4-flash 的训练数据中对 SSML 标签的暴露极少，模型将其视为"不应输出的标记语言"而过滤掉了。
- 结论：此路径在当前模型（deepseek-v4-flash / deepseek-v4）下不可行。换用 Claude 3.5 Sonnet 或 GPT-4o 可能有效，但智增增平台目前不支持。

**路径 B：LLM 标注 + 后端转换（折中方案，实验失败）**
- 原理：不要求模型输出原生 SSML，而是输出简化的韵律标记（如 `【强调】增长30%【/强调】`），后端再转换为 SSML。
- 实验：测试了 `[emphasis]`、`((强调))`、`【重读】` 等多种标记格式。
- 结果：模型偶尔输出标记，但**极不稳定**，有时输出有时不输出，且标记位置经常错位（标在了无关词上）。
- 结论：仍然依赖模型的"听话程度"，deepseek-v4-flash 对这类结构化指令的遵循度不够。

**路径 C：后端规则注入（最终选中）**
- 原理：LLM 只负责生成高质量纯文本对话，SSML 标签完全由后端用正则规则注入。这是"去模型化"的思路——凡是模型做不好的事，就交给规则引擎。
- 实验过程：
  - 先验证了 edge-tts 的 SSML 支持范围：`<break>`、`<emphasis>`、`<prosody>` 均有效（通过直接调用 `edge_tts.Communicate` 测试）
  - 编写了正则规则覆盖最常见的"需要强调"的模式：百分比、金额、年份、大数字
  - 编写了标点规则覆盖"需要停顿"的模式：问号、感叹号、句号、逗号
  - 测试了 SSML 标签的 overhead：一段 2000 字的文本加上 SSML 后，标签约占 15-20% 长度，edge-tts 在 >1800 字符时容易失败，所以设置了截断保护
- 决策理由：100% 可控、不依赖模型、规则可迭代。虽然不如 LLM 原生 SSML 精准（模型知道"哪个词在语义上重要"，规则只知道"哪个词在模式上重要"），但在当前模型约束下，这是唯一可靠的路径。

**实现**
- 函数：`inject_ssml(text) -> str`
- 注入规则：
  - **数据强调**：百分比 `45%`、金额 `3000亿美元`、大数字 `2028` → `<emphasis level="moderate">...</emphasis>`
  - **句尾停顿**：问号 → `<break time="500ms"/>`；感叹号 → `<break time="400ms"/>`；句号 → `<break time="300ms"/>`
  - **过渡停顿**：过渡词+逗号（但是/不过/所以/总之/你看/首先/其次/最后）→ `<break time="200ms"/>`
  - **长句呼吸**：长句中的逗号 → `<break time="150ms"/>`
- 自动包裹：检测是否已有 `<speak>`，无则包裹为 `<speak version="1.0" ...>...</speak>`
- 长度保护：>1800 字符自动截断（SSML 标签增加 overhead，edge-tts 在过长文本下可能失败）

**验证**  
直接调用 edge-tts 库验证了 SSML 支持，确认 `<break>` 和 `<emphasis>` 均有效。试听对比：带 SSML 的版本在"3000亿美元""增长35.6%"等数据点上明显更有重音感，信息传达效率提升。

### 2.3 长文章分块策略

**问题**  
单 prompt 超过 6000 字后，模型输出容易遗漏后半部分内容，且 4096 max_tokens 可能不够输出完整对话（约 3000-3500 中文字）。一篇 8000 字的文章如果要求模型一次生成覆盖全文的对话，输出要么被截断，要么后半部分严重缩水。

**调研过程**  
用户的问题是"**长文章切片升级路径怎么选**"。这不是一个简单的问题，因为"切分"这件事本身就有多个维度：按字数切、按结构切、按语义切、按模型理解切。我们系统性地调研了五条路径：

**路径 A：固定大小切分（Fixed-size Chunking）**
- 原理：设定 chunk_size（如 5000 字）和 overlap（如 500 字），像切香肠一样把文章切成等长段落。overlap 的作用是给下一段提供上下文，避免信息断层。
- 优点：实现极简，不依赖模型，确定性最高。
- 缺点：**语义边界被随机切断**。一个完整的论点可能被切成两半，前半段在一个 chunk 里生成了对它的讨论，后半段在下一个 chunk 里又重复讨论一次；或者更糟糕——后半段因为缺少前半段的铺垫，直接把论点遗漏了。
- 实验：在测试文本上切分后，发现第二章的案例分析被拦腰切断，导致生成的对话中案例只讲了一半。
- 结论：只能作为保底 fallback，不能作为首选。

**路径 B：递归切分（Recursive / Heading-based）**
- 原理：直接利用原文的 HTML 标题层级（H1/H2/H3）作为切分边界。如果原文是知乎专栏、公众号文章，通常自带小标题，可以直接按标题切。
- 优点：天然对齐文章结构，无需 LLM 参与。
- 缺点：**严重依赖原文格式**。很多网页抓取的纯文本丢失了一切格式信息（标题变成普通加粗或纯文本），此时递归切分会失效。此外，如果原文没有小标题（如散文、叙事文），此路径完全不可用。
- 结论：适用场景太窄，不能作为通用方案。

**路径 C：语义切分（Semantic Chunking）**
- 原理：用 embedding 模型（如 text-embedding-3-small）把文章按句子或段落向量化，然后计算相邻段落之间的语义相似度。在相似度骤降的位置切分，得到语义独立的 chunk。
- 优点：最"智能"，切分边界天然是话题切换点。
- 缺点：**成本高、延迟大**。一篇 10000 字的文章需要先切成 50-100 个段落，逐个请求 embedding，再计算相似度矩阵，整个过程可能耗时 5-10 秒。对于 TTFA（Time To First Audio）敏感的场景 unacceptable。此外，embedding 的粒度选择（句子级 vs 段落级）对结果影响很大，调参困难。
- 结论：技术很酷，但性价比低，暂不采用。

**路径 D：Late Chunking（Jina AI 方案）**
- 原理：先将整篇文章输入 LLM，获取每个 token 的上下文 embedding，然后在 embedding 空间中寻找语义断点进行切分。相比传统语义切分，late chunking 利用了 LLM 的深层理解能力，断点更精准。
- 优点：学术界最新方案，切分质量理论上最高。
- 缺点：**需要访问模型的中间层 embedding**，这要求：
  1. 使用支持 late chunking 的专用模型（如 Jina AI 的嵌入模型）
  2. 不能通过 OpenAI-compatible API 调用，必须直接加载模型
  我们的后端通过智增增平台调用 deepseek-v4-flash，完全无法获取中间层 embedding。
- 结论：基础设施不支持，放弃。

**路径 E：大纲先行（Outline-first，最终选中）**
- 原理：先让 LLM 通读全文，提取结构化大纲（每个 section 的标题 + 核心要点）；然后后端根据大纲标题在原文中定位，按大纲边界切分；最后逐 section 生成对话。
- 优点：
  - **语义边界最清晰**：切分点由 LLM 根据文章逻辑决定，而不是由字数决定
  - **覆盖度有保障**：每个 section 的 key_points 被显式写入 prompt，要求模型"必须覆盖"，大幅降低遗漏率
  - **通用性强**：不依赖原文格式，散文也能提取大纲
- 缺点：多一次 LLM 调用（提取大纲），增加约 3-5 秒延迟和少量 token 成本。
- 实验：用 9000 字的测试文章跑通全流程，大纲提取出 5 个 section，全部成功映射到原文位置，生成的对话覆盖了所有关键论点。
- 决策理由：质量最优，且延迟增加在可接受范围内（后台生成场景对 3-5s 不敏感）。NotebookLM 等业界标杆产品也采用类似思路。

**实现**
- 大纲提取：`extract_outline(clean_text)` → `parse_outline(raw)` → `list[{title, key_points}]`
- 文本切分：`_split_by_outline(clean_text, outline)`，按标题在原文中的精确位置切分；如果标题匹配失败，fallback 到 key_point 的模糊匹配（前 20 字）
- 逐段生成：每 section 独立调用 LLM，system prompt 用 `STEP2_CONTINUATION`，user prompt 包含 section_text + key_points + prev_context
- 去重：`_deduplicate_overlap(prev, new)` 比较相邻 chunk 首尾 2 轮，若重复则删除
- 降级：大纲提取失败、section 映射失败、或提取出的大纲为空 → 自动 fallback 到 simple chunking

### 2.4 动态阈值策略

**问题**  
最初代码使用固定阈值 6000 字：≤6000 字 single-shot，>6000 字走分块。但用户敏锐地指出："**你说方案2适合10000字以上是吧，那一万字以内的呢？适合什么方案？**"。这说明固定阈值忽略了两个关键维度：
1. **输出 token 的限制**：模型 max_tokens=4096，实际只能输出约 3000-3500 中文字。一篇 5000 字的原文如果信息密度高（如行业报告），生成的对话可能也要 4000+ 字，已经逼近输出上限。
2. **文本结构差异**：一篇 6000 字的散文和一篇 6000 字的知乎深度分析文，生成策略应该不同。前者结构松散，outline-first 的收益低；后者结构清晰，分块能显著提升覆盖度。

**调研过程**

**第一步：确定单段生成的安全上限**
- 分析：deepseek-v4-flash 的 max_tokens=4096。中文在 LLM 中的 token 比例约为 1:1.3（1 个中文字 ≈ 1.3 tokens），所以 4096 tokens ≈ 3000-3500 中文字。
- 对话文本通常是原文长度的 60-80%。因此：
  - 3000 字原文 → 生成约 2000 字对话（安全）
  - 5000 字原文 → 生成约 3500 字对话（接近上限，偶尔截断）
  - 6000 字原文 → 生成约 4200 字对话（**超出上限，后半截可能被截断**）
- 结论：单段生成的安全阈值应该在 **4000 字** 左右，而不是 6000。

**第二步：确定强制分块的下限**
- 分析：当原文 >8000 字时，即使信息密度低，生成的对话也至少需要 5000+ 字，远超 4096 tokens。
- 实验：测试了 7000 字无结构文本的 single-shot，发现模型自动压缩了后半部分内容，案例和细节大量丢失。
- 结论：**8000 字是硬上限**，超过后必须分块，无论结构如何。

**第三步：中间地带（4000-8000 字）的决策逻辑**
- 分析：这个区间是"灰色地带"。单段生成可能成功，也可能失败；分块能保证覆盖，但增加延迟和衔接风险。
- 决策：引入**结构清晰度**作为第二变量。
  - 如果原文有清晰的小标题/章节结构 → outline-first 能精准切分，收益高
  - 如果原文是线性叙事/散文 → 强行分块反而破坏流畅度，不如 single-shot 赌一把

**第四步：结构检测算法设计**
- 调研了多种结构检测方法：
  - 正则匹配：Markdown 标题、中文编号、阿拉伯数字编号
  - 关键词匹配：引言/背景/分析/结论/总结等章节标志词
  - NLP 方法：用 TextRank 或 BERT 提取关键句，判断是否存在"章节句"
- 决策：采用**正则 + 关键词**的轻量方案。NLP 方法虽然更准，但需要引入额外依赖（jieba/spacy），且对中文网页文本的噪音（广告、导航栏残留）敏感。正则方案足够覆盖 90% 以上的结构化文章。

**最终决策**
```
< 4000 字          → 单段生成（single-shot）
4000–8000 字 + 有结构 → outline-first
4000–8000 字 + 无结构 → single-shot
> 8000 字          → 强制 outline-first（失败则 fallback to simple chunking）
```

**结构检测规则** (`_has_clear_structure`)
- Markdown 标题（`##` / `###`）
- 中文编号（`一、` / `（一）`）
- 阿拉伯数字编号（`1.` / `2、`，3 处以上）
- 章节关键词（引言/背景/分析/结论/总结等，前 3000 字内出现 3 个以上）

**工程收益**
- 避免"一刀切"：短篇散文不走 outline，避免不必要的延迟和衔接问题
- 保证覆盖：长文/结构化文章强制分块，降低遗漏率
- 自适应：同一篇文章，如果用户粘贴的是"带小标题的知乎回答"走 outline-first；如果粘贴的是"一段微信聊天转录"走 single-shot

**实现**
- 核心判断逻辑在 `generate_structured_dialogue` 入口：
  ```python
  use_outline = length > 8000 or (length > 4000 and _has_clear_structure(clean_text))
  ```
- `_has_clear_structure` 实现（轻量正则，无额外依赖）：
  - Markdown 标题：`re.search(r'^#{2,4}\s+', text, re.MULTILINE)`
  - 中文编号：`re.search(r'^[一二三四五六七八九十]+[、．.]\s*', text, re.MULTILINE)`
  - 括号中文编号：`re.search(r'^（[一二三四五六七八九十]+）', text, re.MULTILINE)`
  - 阿拉伯数字编号：`len(re.findall(r'^\d+[、.．]\s*\S', text, re.MULTILINE)) >= 3`
  - 章节关键词：预定义 15 个关键词（引言/背景/现状/分析/案例/结论/总结/展望/建议/核心/趋势/数据/影响/观点/原因/结果），统计前 3000 字内出现次数，≥3 视为有结构
- 策略分支：
  - `not use_outline` → 直接调用 `_generate_single_dialogue` 或带 `opening_text` 的 single-shot
  - `use_outline` → 先 `extract_outline` → `_split_by_outline` → 逐 section 生成 → `_deduplicate_overlap`
  - outline-first 失败（outline 为空或 section_chunks 为空）→ logger 记录后自动 fallback 到 `_split_text_chunks`

**验证**
- 编写了 `test_dynamic.py` 覆盖五种场景（全部通过）：
  1. 短文（<4000 字，无结构）→ 日志确认 `Generation strategy: single-shot`
  2. 中等长度无结构（4000–8000 字）→ 日志确认 `single-shot`
  3. 中等长度有结构（Markdown 标题，4000–8000 字）→ 日志确认 `outline-first`
  4. 长文（>8000 字，无结构）→ 日志确认 `outline-first`
  5. 中等长度有结构 + 带开场白 → 日志确认 `outline-first`
- 测试方法：mock `_call_ai` 避免真实 LLM 调用，通过日志捕获确认策略分支正确。

### 2.5 角色升级与提示词重构

**问题**  
最初系统使用"小羊/小姜"作为固定角色名，存在两个深层问题：
1. **定位冲突**：小羊被设定为"知识面更广、更理性"，小姜是"更接地气、更感性"，但测试中发现模型经常让两个角色说同样的话，缺乏真正的功能分工。
2. **角色区分度不足**：两个角色虽然有"性格"描述，但模型很难把抽象的"性格"转化为具体的语言差异。输出经常出现"串台"——小姜突然开始长篇总结，小羊突然开始感性吐槽。

**调研过程**

**方案 A：增加更详细的性格描述（基线改进）**
- 原理：在 system prompt 里写更多关于小羊和小姜的性格、背景、说话习惯。
- 实验：把角色描述从 3 行扩展到 15 行，包括"小姜是北方人、喜欢看综艺、说话带口头禅"等细节。
- 结果：模型完全忽略这些细节，输出没有任何变化。推测原因：过多的非结构化描述对模型是噪音，它无法从中提取"行为规则"。
- 结论："给模型讲性格"这条路走不通。

**方案 B：Few-shot 示例驱动（部分有效）**
- 原理：不给模型讲"性格"，而是直接给它看 3-5 轮示例对话，让它模仿。
- 实验：在 prompt 中加入高质量示例（小羊总结型 vs 小姜质疑型）。
- 结果：模型确实会模仿示例的句式，但**模仿的是表层结构，不是深层功能**。比如小羊学会了用"你看"开头，但小姜也开始用"你看"；小姜学会了反问句，但小羊也开始反问。
- 结论：Few-shot 能提升语言风格的一致性，但无法保证"功能不串台"。

**方案 C：语言指纹 + 行为不变量（最终选中）**
- 原理：不给模型讲"性格"，而是给它讲**行为规则**和**语言指纹**。
  - **语言指纹**：每个角色有 3-5 个固定口头禅和句式模板。这些不是"建议"，而是"约束"——模型被明确告知"男声必须这样说"。
  - **行为不变量**：每个角色有不可变更的功能。男声=总结+连接，女声=质疑+追问。如果模型让男声去质疑，那就是 bug，必须修正。
- 实验：重构 system prompt，去掉所有"性格描述"，替换为：
  - 男声：习惯用语"你看""换句话说""这里面有几个层面"；句式先给结论再展开；绝对禁忌：不使用反问句
  - 女声：习惯用语"说实话""我有点好奇""那岂不是"；句式从个人体验出发提问；绝对禁忌：不做长篇总结
- 结果：角色区分度显著提升，串台率从约 30% 降至 <5%。
- 决策理由：把"抽象性格"转化为"具体行为规则"，模型遵循度更高。这是系统工程方法，不是 prompt 工程技巧。

**实现**
- 重写 `STEP2_SYSTEM`、`STEP2_CONTINUATION`、`OPENING_SYSTEM`、`EVAL_SYSTEM`
- 替换 `VOICE_MAP`（角色称呼从"小羊/小姜"改为"男声/女声"，后端预留自定义配置扩展接口）
- 升级 `parse_dialogue` 正则和 `validate_dialogue_format` 校验集合
- 新增信息核对机制：生成前列出信息核对清单，生成后自查覆盖度
- 新增追问链设计：女声必须遵循四层追问链（事实→原因→影响→行动）

**验证**
- 连续 12 轮对话测试：角色语言指纹清晰，男声自然使用"你看""拆成两个层面"，女声自然使用"等一下，我有点好奇"
- 串台率：0 处（violations: male=0, female=0）

### 2.6 SSML 规则扩充

**问题**  
Phase 1 基础 SSML 规则不够精细：英文缩写（GDP、AI、CEO）被 TTS 读成单词而非字母，反问句和设问句缺少特殊停顿处理。

**调研过程**

**英文缩写拼读**
- 问题：edge-tts 把"GDP"读成"格德普"（模仿英语发音），而不是"G-D-P"。
- 方案 A：在 inject_ssml 中用正则匹配 2-5 个大写字母，替换为 `<say-as interpret-as="characters">GDP</say-as>`
- 踩坑：最初用 `\b([A-Z]{2,5})\b`，但 Python 的 `\b` 在 Unicode 模式下对中英文混排判断错误（中文字符也被视为 `\w`），导致匹配失败。
- 修复：改用 `(?<![a-zA-Z])([A-Z]{2,5})(?![a-zA-Z])`，用否定前后瞻替代 word boundary。
- 验证：测试 GDP、AI、CEO、FSD、NOA 等缩写，均正确读为字母。

**反问句短停顿**
- 问题：反问句（"难道不是吗？"）不需要给听众思考时间，但普通问句需要 0.9s 停顿。两者不能共用同一规则。
- 方案：检测反问标记词（难道/何必/岂不是/怎么会/谁不知道/不是已经/有什么），将反问句后的停顿从 500ms 缩短为 300ms。
- 实现难点：inject_ssml 的通用替换是先统一把所有问号替换为 `<break time="500ms"/>`，再做其他替换。如果直接加反问规则，会被通用规则覆盖。
- 修复：采用"占位符保护"策略——先用占位符（`\x01`/`\x02`）保护反问句问号，再做通用替换，最后恢复为短停顿。

**实现**
- 英文缩写：正则 `(?<![a-zA-Z])([A-Z]{2,5})(?![a-zA-Z])` → `<say-as interpret-as="characters">...</say-as>`
- 反问句检测：检测标记词，占位符保护 → 通用替换 → 恢复为 300ms break

### 2.9 Chunk 间过渡句

**问题**

**调研**

### 3.1 情感标签注入

**问题**  
当前 TTS 输出是单调的，所有对话用同样的语速和音调，听久了会产生"机械感"。真实播客中，主播在提到惊人数据时会兴奋，在提出尖锐问题时会放慢语速，在深入思考时声音会低沉。

**调研**
- 直接测试验证了 edge-tts 对 `<prosody rate="..." pitch="...">` 的完整支持：
  - rate: fast / slow / medium 及百分比均有效
  - pitch: +10% / -10% / low / high 及百分比均有效
  - 组合属性和嵌套标签均正常生成音频
- 踩坑：测试过程中 `pitch="-10%"` 和组合属性曾短暂出现 `NoAudioReceived`，但复测确认是 edge-tts 服务端瞬时故障，非功能不支持。

**方案对比**
- 方案 A：后端规则判断情绪（关键词匹配"惊人""突破"→兴奋）。缺点：规则难以覆盖所有语境，误判率高。
- 方案 B（选中）：让 LLM 在生成对话时为每轮标注情绪，后端只做映射。LLM 对语境的理解远胜规则。

**情绪体系**
| 情绪 | 触发场景 | Prosody 参数 |
|------|---------|-------------|
| 平静 | 正常讨论、理性分析（默认） | 无 prosody |
| 兴奋 | 惊人数据、重大突破 | `rate="fast" pitch="+10%"` |
| 疑问 | 尖锐提问、表示不解 | `rate="slow" pitch="+5%"` |
| 沉思 | 深入思考、推演后果 | `rate="slow" pitch="-5%"` |

**实现**
- Prompt：在 `STEP2_SYSTEM` 和 `STEP2_CONTINUATION` 中新增"情绪标注（必须执行）"要求
- 输出格式：`男声[兴奋]：...` / `女声[疑问]：...`
- `parse_dialogue` 正则升级：`^(男声|女声)(?:\[([^\]]+)\])?[：:]\s*(.+)`，兼容旧格式（无情绪标签也正常解析）
- TTS 链路：`tts_script` / `_tts_script_segment` 从 script item 读取 `emotion` 字段，`_tts_one` 在 `inject_ssml` 之后、`<speak>` 包裹之前注入 `<prosody>`
- 截断逻辑提前到 prosody 注入之前，避免破坏 XML 结构

**验证**
- 普通文章：8 轮 → 7 平静 + 1 疑问，模型能准确按语境选择
- 戏剧性文章（比亚迪 300 万辆 vs 特斯拉）：14 轮 → 7 平静 + 4 疑问 + 3 沉思

### 3.2 角色稳定性增强

**问题**  
当前偶尔出现"串台"现象——男声突然开始质疑，女声突然开始长篇总结。这在长文章 outline-first 的多个 section 续写中尤为明显。随着对话轮数增加，模型对角色约束的记忆力衰减。

**调研**
- 2025 年研究（Chain of Guidance、Doppelgänger Method）证实：角色一致性是系统工程问题，最稳定的方案是"语言指纹 + 行为不变量 + 周期性重申"。
- 我们已有语言指纹和行为不变量（见 2.5），但缺少**周期性重申**和**具体示范**。

**方案对比**
- 方案 A：只在 system prompt 开头写角色设定。缺点：长文本生成时，模型到后半段会"忘记"角色约束。
- 方案 B（选中）：三管齐下——角色锚点（硬规则）+ 角色示范（few-shot）+ 生成后自查 + 后端监控。

**实现**

**角色锚点**（新增于 `STEP2_SYSTEM` 和 `STEP2_CONTINUATION`）：
1. 男声绝对不说"说实话""我有点好奇""那岂不是""等一下"
2. 女声绝对不说"你看""换句话说""这里面有几个层面"
3. 男声的功能是"总结+连接"，女声的功能是"质疑+追问"，两者不可互换

**角色示范**（2 轮精简示例，~100 字）：
- 男声[平静]：你看，这个问题可以拆成两个层面。第一层是市场规模，第二层是盈利模式。
- 女声[疑问]：等一下，我有点好奇——如果成本这么高，消费者真的愿意买单吗？

**生成后自查**（`STEP2_SYSTEM` 新增步骤）：
- 检查男声台词中是否出现了女声标志性用语——如果出现，立即删除或重写
- 检查是否有角色做了对方的功能（男声质疑、女声总结）——如果有，立即修正

**后端监控**（新增 `_check_role_consistency(dialogue)`）：
- 客观记录每次生成的串台次数，用于观察趋势
- 在 `generate_structured_dialogue` 的所有生成路径（single-shot / outline-first / fallback）后自动调用

**验证**
- 12 轮对话测试：**0 处串台**（violations: male=0, female=0）
- 语言指纹清晰：男声自然使用"你看""拆成两个层面"，女声自然使用"等一下，我有点好奇"

### 3.3 对话节奏控制（去AI味）

**问题**
Phase 1和2的前序优化解决了停顿、强调、情绪、角色稳定，但播客整体仍有一股"AI味"。核心原因不是TTS引擎语料少，而是三个结构性缺陷：
1. **文本太干净**——LLM生成的对话像剧本，没有真人口语的犹豫、重复、自我修正、填充词。真人会说"嗯……那个……我觉得吧"，我们的对话没有这些"瑕疵"。
2. **逐句拼接的断裂感**——每句话独立合成，TTS引擎不知道上下文，语气、语速没有连续性。
3. **零互动**——没有笑声、叹气、听到惊人数据时的倒吸气，两个人像轮流念稿。

**调研**

**问题1（文本干净）的可解性**
- 端到端模型（NotebookLM、豆包播客API、Dia TTS）直接一次性输出双人对话音频，自然涌现笑声、抢话、重叠。但这些方案要么黑盒不可控，要么不支持中文。
- 在拼接式架构下（LLM生成文本→逐句TTS→ffmpeg拼接），唯一能做的是**让文本本身更像口语**。

**问题2和3的可解性**
- **笑声**：edge-tts/Azure/豆包/讯飞/百度，公开文档均未明确支持中文笑声标签。ElevenLabs v3支持`(laughs)`但英文为主。Dia-1.6B支持但中文差。**中文笑声是行业空白**。
- **叹气/轻声**：可通过SSML `<prosody volume="soft">` 部分模拟。
- **停顿**：已有 `<break>` 支持，但只在句尾。句中停顿（思考、犹豫）需要新标记。

**标记格式对比**
| 格式 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| 行内大括号 | `男声：这个数据{笑}有点夸张` | 自然 | 解析复杂，与文本混合 |
| 前缀标记 | `[笑]男声[兴奋]：台词` | 解析简单 | 笑声只能放句首 |
| 独立meta行 | `META: laugh` | 不污染文本 | 模型遵循度低，格式容易崩 |
| XML标签 | `<laugh>台词</laugh>` | 结构化 | 模型输出XML遵循度低 |

**最终选择：混合方案**
- **Prompt层面**：要求模型使用口语填充词（"嗯……""那个……""等一下等一下"）、自我修正、自然重复，从根本上让文本"不干净"。
- **标记层面**：采用句中标记 `[停顿]` 和范围标记 `[轻声]...[/轻声]`，由后端映射为SSML。`[笑]`、`[叹气]` 当前引擎不支持音频生成，暂不在prompt中强制要求，但保留扩展接口。

**实现**
- **Prompt升级**：`STEP2_SYSTEM` 和 `STEP2_CONTINUATION` 新增第6条"口语化与自然感（必须执行——这是去AI味的核心）"：
  - 允许口语填充词、自我修正、自然重复、打断感表达
  - 句中停顿用 `[停顿]` 标记
  - 轻声用 `[轻声]...[/轻声]` 标记
  - 明确要求"不要在每句话都用标记，只在真正有语气变化的地方使用，自然第一"
- **SSML注入升级**：`inject_ssml` 新增步骤7：
  - `[停顿]` → `<break time="400ms"/>`
  - `[轻声]...[/轻声]` → `<prosody volume="soft">...</prosody>`
- **向后兼容**：`parse_dialogue` 无需改动——标记在text内部，解析后自然保留，由inject_ssml统一处理。

**验证**
- 逻辑路径验证：
  - `[停顿]` 正确替换为 `<break time="400ms"/>`，不破坏已有SSML规则
  - `[轻声]...[/轻声]` 正确嵌套在 `<prosody>` 内，支持已有 `<emphasis>` 嵌套
  - TTS流水线顺序（inject_ssml → 截断 → emotion prosody → _wrap_ssml）保持正确，嵌套SSML合法
- 测试脚本：`backend/test_rhythm_markers.py`（Windows环境Python运行受限，逻辑已逐行人工验证）

**已知限制**
- `[笑]` 和 `[叹气]` 在当前edge-tts架构下无法转化为音频效果（引擎不支持laughter/sigh标签）。这是**拼接式TTS的行业天花板**，非prompt或规则可解。
- 真正的笑声/重叠/抢话需要端到端对话模型（如NotebookLM、豆包内部播客模型），但这类方案黑盒不可控，丢失现有全部后处理优化。

## 四、系统架构变化

```
输入文本
    │
    ▼
动态阈值判断 ──→ <4000字 ──────→ single-shot 生成
    │              4000-8000有结构 → outline-first
    │              4000-8000无结构 → single-shot
    │              >8000 ─────────→ outline-first (fallback chunking)
    ▼
生成对话文本（含情绪标签）
    │
    ▼
parse_dialogue → 提取 speaker + text + emotion
    │
    ▼
inject_ssml(强调数字/金额/百分比 + 英文缩写拼读 + 反问句停顿 + [停顿]/[轻声]口语标记)
    │
    ▼
edge-tts 逐句合成（按 voice_map 选择声线）
    │
    ▼
 emotion → <prosody rate/pitch> 注入
    │
    ▼
_compute_pause → ffmpeg 插入静音片段
    │
    ▼
ffmpeg concat → 最终 MP3
    │
    ▼
_post_process_audio(响度标准化 + 可选背景音)
```

**关键函数**
| 函数 | 职责 |
|------|------|
| `generate_structured_dialogue` | 核心调度：动态阈值 + 生成策略选择 |
| `extract_outline` / `_split_by_outline` | 大纲提取与文本切分 |
| `_generate_single_dialogue` | 单段生成 prompt 组装 |
| `_deduplicate_overlap` | chunk 间去重 |
| `inject_ssml` | 规则注入 SSML 标签（emphasis / break / say-as / prosody）+ 口语标记映射（[停顿] / [轻声]） |
| `_emotion_to_prosody` | 情绪 → prosody 属性映射 |
| `_compute_pause` | 停顿时长计算 |
| `_generate_silence` | ffmpeg 生成静音 MP3 |
| `_check_role_consistency` | 角色一致性后处理检测 |
| `tts_script` | TTS 流水线：合成 → 情绪 prosody → 插入静音 → 拼接 |

## 五、已知问题与限制

| 问题 | 影响 | 优先级 |
|------|------|--------|
| SSML 规则仍基于正则，复杂语气可能不准 | 特定语境下的停顿/强调可能错位 | 中 |
| 长文章 chunk 间衔接 | 话题切换时偶尔有生硬感（已改善但未完全消除） | 中 |
| TTS 片段过多时 ffmpeg concat 慢 | 100+ 轮对话时拼接耗时增加 | 低 |
| 模型输出偶尔不遵守格式 | 极少数情况不输出情绪标签或 `男声/女声` 格式 | 低 |
| 女声偶尔做简短总结 | 角色锚点未完全阻止功能边界的模糊地带 | 低 |
