# TTS 战略决策全过程记录

**记录日期**：2026-05-11
**决策人**：播刻技术负责人 + Claude Code
**核心问题**：在"播客创作者平台"定位下，如何在千元/月预算内选择最优 TTS 架构？

---

## 一、问题起源

### 1.1 原始痛点
播刻当前使用 edge-tts 拼接架构（LLM 文本 → 逐句 TTS → ffmpeg 拼接 → MP3）。Phase 1/2 已完成大量优化：
- 智能停顿插入（`_compute_pause`）
- SSML 韵律增强（`inject_ssml`：强调数字/金额/百分比、英文缩写拼读、反问句短停顿）
- 长文章 outline-first 分块策略
- 情感标签 + prosody 注入（4 种情绪 → rate/pitch）
- 角色稳定性（语言指纹 + 行为不变量）
- 口语化标记（`[停顿]`、`[轻声]...[/轻声]`）

但播客仍有明显"AI感"。用户最初认为是"语料库太少"，实际诊断后发现是三个结构性问题：
1. **文本太干净**——LLM 生成像剧本，没有真人口语的犹豫、重复、自我修正
2. **逐句拼接的断裂感**——每句话独立合成，TTS 引擎不知道上下文
3. **零互动**——没有笑声、叹气、重叠语音

### 1.2 第一次追问
用户要求"把技术壁垒、成本、效果立体对比"。我给出了 7 个方案的 3D 决策矩阵（edge-tts / Azure / 豆包 / Fish Speech / ChatTTS / CosyVoice / ElevenLabs）。

**关键结论（第一轮）**：
- 端到端（NotebookLM、豆包）自然度最高，但控制粒度极低（黑盒）
- 拼接式（edge-tts、Azure）控制粒度高，但拼接感不可避免
- 只要架构是"逐句合成再拼接"，无论换哪个商业 API 都无法根本解决 AI 感

### 1.3 第二次追问（转折点）
用户纠正了我的方向："我们的产品目标是打造播客创作者平台，那是不是需要非常细致的可调节颗粒度呢？成本如果控制在千元内我是可以接受的。"

**问题重新 framing**：
- 不是"自然度最高 vs 控制粒度最高"二选一
- 而是"在创作者平台定位下，哪个方案能在足够自然的前提下提供创作者需要的控制工具"
- 预算约束：~1000 元/月

## 二、调研阶段

### 2.1 调研范围
针对"可控 + 端到端"这个交叉领域，重点调研了：

| 方案 | 类型 | 调研重点 |
|------|------|---------|
| MaskGCT | 开源/本地 | 是否支持 duration/pitch/emotion 的细粒度控制 |
| Spark-TTS | 开源/本地 | BiCodec 解耦 Token 对 pitch/speed/prosody 的控制能力 |
| Qwen3-TTS | 商业 API | 自然语言指令控制的粒度，是否支持多角色 |
| Fish Speech | 开源/本地 | 多角色单次推理、标签控制体系 |
| Azure Official | 商业 API | 15 种风格 + styledegree + HD 语音的精细程度 |

### 2.2 关键发现

#### 发现 1：MaskGCT 控制粒度不足
- 支持 coarse-grained total duration（总时长控制）和 zero-shot emotion（通过语音 prompt）
- **不支持细粒度 pitch 控制**，控制是 utterance-level 而非 segment-level
- 需要 GPU 本地部署
- 结论：不满足创作者平台的"细粒度"要求

#### 发现 2：Spark-TTS 档位太粗
- 基于 Qwen2.5 + BiCodec，Semantic Token + Global Token 解耦设计
- 支持 gender / pitch / speed 的**5 档标签控制**（very_low/low/moderate/high/very_high）
- 性别控制准确率 99.77%，RTF 3.2x
- **但不支持单次多角色推理**
- 结论：5 档标签对创作者来说太粗糙，无法精确调节

#### 发现 3：Qwen3-TTS 有致命缺陷（对播客场景）
- 支持自然语言指令控制：语速、情感、语调、停顿（`#1`/`#2`/`#3` 标记）、强调
- 声音克隆仅需 3 秒样本
- **致命缺陷：不支持单次请求合成多个不同声音**
- 双人播客仍需逐句调用 API + 拼接，失去了端到端的核心优势
- 结论：指令控制很友好，但播客场景下和 Azure 一样仍是拼接式

#### 发现 4：Fish Speech 是唯一"真端到端+多角色"方案
- 原生支持 `<|speaker:0|>` / `<|speaker:1|>` **单次推理生成完整双人对话**
- 支持 `[laugh]`、`[sigh]`、`[inhale]`、`[exhale]` 等非语言声音
- 15,000+ 情感标签，词级控制 `(angry)`、`(sad)`、`(excited)`、`[whisper]`
- 中文 WER 0.54%
- 部署需求：4GB+ 显存，SGLang 推理引擎
- **稳定性风险**：自回归模型可能中途变声
- **控制粒度局限**：标签级而非参数级，不支持毫秒级停顿调节

#### 发现 5：Azure 官方 API 控制维度最全
- `mstts:express-as`：15+ 中文风格（chat/cheerful/angry/sad/gentle 等）
- `styledegree`：情感强度 0.01~2.0 连续可调
- 完整 SSML：`<break>` 精确到毫秒、`<emphasis>` 逐词、`<prosody>` 逐句
- 和 edge-tts **同一底层引擎**，改造成本极小
- 仍是拼接式，无笑声
- 成本：~100 元/100万字符

## 三、思考阶段

### 3.1 "创作者平台"重新定义了优先级

最初以为自然度是第一优先级。但用户明确后，优先级重新排序：

| 创作者需求 | 优先级 | 说明 |
|-----------|--------|------|
| 每句话的情绪、语速、风格可控 | P0 | utterance 级控制，创作者必须能决定"这句怎么说" |
| 特定词的强调、轻声、停顿 | P0 | word 级控制，信息传达效率 |
| 多角色音色稳定区分 | P0 | 双人播客的基础 |
| 笑声、叹息、呼吸 | P1 | 高级需求，锦上添花 |
| 抢话、重叠、互动感 | P1 | 极致自然度，非必须 |
| 每个字的音高曲线 | P2 | 音频工程师需求，非播客创作者需求 |

**关键认知**：播客创作者要的是"导演工具"（告诉 AI 这句怎么演绎），不是"音频工作站"（自己画 pitch 曲线）。

### 3.2 技术路线的本质矛盾

| 路线 | 自然度 | 控制粒度 | 多角色单次推理 | 代表 |
|------|--------|---------|---------------|------|
| 拼接式商业 API | 中 | **极高** | ❌ | Azure、edge-tts |
| 端到端黑盒 | **极高** | 极低 | ✅ | NotebookLM、豆包 |
| 端到端开源可控 | 高 | 中（标签级） | ✅ | Fish Speech |
| 端到端商业指令 | 高 | 中（指令级） | ❌ | Qwen3-TTS |

**结论**：当前技术发展阶段，"端到端"和"细粒度控制"仍然是互斥的。Fish Speech 在两者间做了最好的平衡，但控制粒度也只是"标签级"而非"参数级"。

### 3.3 为什么"双引擎"是唯一的理性选择

单一方案无法满足创作者平台的所有场景：
- **商务/知识播客**需要精确控制每句话的风格和强调 → Azure 更适合
- **娱乐/故事播客**需要笑声、互动感、无拼接感 → Fish Speech 更适合
- 作为平台，应该让**创作者选择**，而不是替创作者决定

预算核算：
- Azure：~100 元/月（按 100 万字符计）
- Fish Speech GPU（AutoDL RTX 4090）：~600 元/月
- 总计：~700 元/月 < 1000 元预算

## 四、决策阶段

### 4.1 最终策略：双引擎并行

| 引擎 | 定位 | 改造优先级 | 成本/月 |
|------|------|-----------|---------|
| **Azure 官方 API** | 精细控制引擎（默认） | **现在** | ~100 元 |
| **Fish Speech 本地** | 自然演绎引擎（高级模式） | 验证后 | ~600 元 |

### 4.2 为什么 Azure 是第一优先（不是 Fish Speech）

1. **改造成本极小**：tts_benchmark.py 已支持 Azure，只需申请 Key 即可验证
2. **现有优化全部兼容**：SSML 注入、停顿逻辑、情绪 prosody、角色声线，无需重写
3. **控制维度跃升**：从 edge-tts 的 0 种风格 → 15 种风格 × 2.0 强度，这是立竿见影的提升
4. **风险最低**：成熟商业 API，不引入 GPU 运维、模型稳定性等未知数
5. **成本最低**：验证阶段几乎零成本

### 4.3 Fish Speech 的接入时机

条件：
- Azure 验证完成，确认拼接式天花板确实无法满足高级创作者
- 完成 GPU 服务器部署和稳定性测试
- 重写 TTS 流水线（整段对话 → Fish 格式 → 单次推理）
- 设计 Fish 标签与现有标记体系的映射

### 4.4 Qwen3-TTS 的排除理由

虽然自然语言指令控制很吸引人，但：
- 不支持单次多角色 → 播客场景下仍是拼接式
- 和 Azure 比，控制粒度更模糊（"语速较快" vs `<prosody rate="fast">`）
- 改造成本不低（需要接入 DashScope SDK、重写 prosody 逻辑）
- 建议持续观察，等阿里云支持原生多 speaker 后再评估
